**Ключевое решение инкремента 1 — чем заливать.** Заливка цветом фона берёт
**медиану пикселей самой полосы**, а не участка рядом. Обоснование: выжженный
текст — это разреженные глифы на однородном фоне (реальное покрытие ~15 %),
поэтому медиана и есть фон, причём при любой полярности: чёрная шапка с белыми
буквами зальётся чёрным, белый инфо-бар с чёрными — белым. Цветные кадры
заливаются посередине поканально, поэтому полоса не «сереет» и цветной Doppler
не ломает детектор цвета.

Граница применимости (задокументирована тестом `test_solid_band_fills_with_its_own_colour`):
если вендор выжжет полосу, занятую текстом **более чем наполовину**, заливка
выродится в цвет текста — ничего не скроет, но и ничего не раскроет. На корпусе
245 файлов таких классов нет; на случай чужого аппарата есть чекбокс.

**Производительность.** Выключено или маскировать нечего → возвращается тот же
массив, ноль аллокаций. Включено → одна копия кадра (`np.empty_like`) + одна
запись среза. Сознательно **без переиспользуемого буфера**: результат уходит в
`_current_frame` и читается другими виджетами, переиспользование буфера молча
перезаписало бы чужие данные. Заголовок файла читается один раз на файл
(`stop_before_pixels`), кэш на 256 записей.

**Ключевое решение инкремента 2 — откуда берётся геометрия экспорта.** Воркер
экспорта идёт по пулу потоков и ничего не рисует: он не может спросить виджет ни
про выключатель, ни про открытый файл. Поэтому `frame_masker(source_path, enabled=…)`
строит **отдельный фильтр, привязанный к экспортируемому файлу**: полоса и кламп
по панели разрешаются из заголовка **того самого файла**, который пишется, — ровно
как превью этого файла в вьюере. Экспорт из галереи не обязан совпадать с открытым
клипом, а «что видно на экране — то и в файле» держится одним выключателем
`anonymize_frames`: его читает и вьюер, и экспорт (через `viewer.phi_masking_enabled`).
Свой экземпляр фильтра на экспорт заодно не пускает кэш заливки этого клипа в
фильтр GUI-потока.

**Маска ставится до энкодера, а не после конвертации.** Кадр маскируется в той же
репрезентации, в которой его получает вьюер (для DICOM — RGB), и только потом
превращается в BGR для `cv2.VideoWriter`; исключений для «уже преобразованных»
кадров нет, иначе часть кадров ушла бы в файл незамаскированной.

**MP4 из MP4.** Выключенная маска оставляет прежний быстрый путь — побайтовое
копирование файла. Включённая маска требует декодирования кадров, поэтому клип
перекодируется тем же воркером (`-map_metadata -1` при этом не нужен: свежий
контейнер пишет сам `cv2.VideoWriter`, метаданные исходника в него не попадают).

**Как проверить вручную:** открыть Samsung-цикл — шапка с ФИО/ID/датой должна
стать однородной; включить M-mode — полоса в развёртке исчезает; снять чекбокс
«Скрывать данные пациента на кадре» — кадр возвращается как есть, без перезагрузки;
и главное — **экспортировать клип в MP4 из галереи** и открыть результат: шапка
однородна, верхняя полоса калибровки (у Samsung — до первой строки панели, 100 из
884) не задета.

## 3. Чистка тегов

### 3.1 Базовый список (по scope «убрать ФИО»)

- `PatientName` → пусто / псевдоним
- `PatientID` → `ANON-<hash>` или пусто
- `OtherPatientIDs`, `OtherPatientIDsSequence` — **добавлено по результатам проверки**

### 3.2 Почему добавлены `OtherPatientIDs*`

На корпусе GE: `OtherPatientIDs = '?????03_46825'` и `OtherPatientIDsSequence` —
буквальный дубль `PatientID`. В сыром файле там будет реальный идентификатор, и он
**не покрывался** списком v2. Это реальный канал утечки, а не теоретический.

### 3.3 Квазиидентификаторы (опция, по умолчанию OFF)

`AccessionNumber`, `StudyID` (содержит дату/время), `PerformedProcedureStepID`.
Удалять или нет — зависит от сценария: для «передал коллеге» они полезны для сверки,
для публикации — лишние.

**`PatientSize` / `PatientWeight` сохраняем обязательно**: они почти везде заполнены и
участвуют в BSA-индексации измерений. Удаление исказит клинический вывод.

### 3.4 Сохраняем всегда

`SequenceOfUltrasoundRegions` (калибровки Doppler/M-mode, геометрия панелей),
`PixelSpacing`, UID, приватные блоки (по умолчанию, см. §7).

## 4. Маска пикселей

### 4.1 Алгоритм

```text
spec = profile[(vendor, H, W)]                       # top, clamp_to_panel, preserve_ui
if BurnedInAnnotation == "NO": spec.mask_off()        # правило 14
plan = resolve(spec, override[(vendor,H,W)], regions) # кламп: верх ≤ min(panel.y0)
frame[y0:y1, x0:x1] = background(frame)               # медиана внешних строк, fallback 0
```

### 4.2 Кламп

Работает только при наличии регионов. Для 800/884/480 — есть; для 1080×1920 и 668×1280 —
**нет**, поэтому там профильный процент единственный ограничитель.

### 4.3 Правило для `preserve_ui` (668×1280) — уточнение правила из v2

В v2 правило звучало «маска = max(профиль, найденное)». Для 668×1280 оно **вредно**:
профиль там 0.0 (верх — UI анализа «3 Point Contour»), а детектор текста честно найдёт
текст и «расширит» маску — то есть сотрёт интерфейс анализа.

Уточнённое правило:

```text
маска = профиль ∪ (найденное ∩ разрешённая_зона)
для классов preserve_ui: найденное НЕ расширяет маску, только предупреждает
```

### 4.4 M-mode и производные виды — поведение маски

**Устройство (проверено по коду):** `MModeWidget` — отдельный виджет, добавляемый в
`_mmode_vertical_splitter` главного окна. При включении M-mode окно просмотра становится
ниже, изображение масштабируется в уменьшившийся вьюпорт, полоса M-mode появляется
отдельным виджетом под ним. Колонка M-mode извлекается из кадра функцией
`extract_mmode_column(frame, start, end, num_samples)` — из `viewer_widget._current_frame`
(`viewer_widget.py:1774, 1922`) и из кэшированных кадров
(`mmode_widget.recalculate_from_frames`, `mmode_widget.py:309`).

**Ответ на вопрос «будет ли маска уменьшаться»:** да, и это правильно. Маска задана
в **координатах изображения** (строки исходного кадра), поэтому при уменьшении вьюпорта
она масштабируется вместе с картинкой: на экране полоса становится визуально тоньше, но
накрывает ровно те же строки (например, 0…100 из 884), то есть тот же текст. Настраивать
ничего не нужно.

**Два условия, без которых это перестаёт работать:**

1. **Маска применяется к исходному кадру, а не как оверлей в координатах виджета.**
   Если реализовать её как «верхние 12 % высоты виджета», то при укороченном вьюпорте
   12 % виджета ≠ 12 % изображения — полоса уедет и либо оставит текст, либо заденет
   изображение. Именно поэтому фильтр стоит до `show_frame()`, а не внутри отрисовки.
2. **Колонка M-mode строится из замаскированного кадра.** Живая колонка берётся из
   `_current_frame` — если маска стоит на пути кадра, она уже замаскирована. Но
   `recalculate_from_frames(cached_frames, …)` читает **кэшированные** кадры: если кэш
   хранит оригиналы, пересчитанная развёртка будет построена из незамаскированных
   пикселей. Требуется либо маскировать кадры и в этом пути, либо затирать
   соответствующие отсчёты в готовой колонке.

**Что видно в полосе M-mode.** Линия сканирования пересекает замаскированную полосу, и
выборка там даёт цвет заливки — в развёртке появляется ровный (тёмный) участок у
соответствующих глубин. Косметическая артефактная полоса сверху. Альтернатива хуже:
текст статичен, поэтому без маски каждый кадр даёт в развёртке **одинаковые значения** —
на экране возникает постоянная по времени светлая полоса, буквально построенная из
пикселей вплавленного имени. Прочитать её нельзя, но это PHI-производные пиксели на
экране.

**Оговорка про калибровку.** Маска **не** должна применяться к кадрам, на которых
работают автокалибровки (`depth_scale_detector`, `samsung_tick_detector`,
`doppler_grid_detector` ищут метки глубины и сетку, которые у части вендоров живут у
верхней кромки). Правило: **калибровка и расчёты — на оригинальных кадрах; маска —
только для отображения и экспорта**. Исключение — колонка M-mode: это отображение, её
строим из замаскированного кадра. С клампом по панели полоса не заходит в сектор
(800: 0…90 при панели от 90; 884: 0…100 при панели от 100; 480: 0…57 при панели от 90),
поэтому риск для калибровки минимален; для strain-разрешений без регионов
(1080×1920, 0.14) риск есть — там обязательны превью и флаг `preserve_ui`.

**Экспорт снимка.** `_save_viewer_image()` делает `grab()` только виджета просмотра,
поэтому в режиме M-mode сохранится **только 2D-изображение без полосы M-mode**. Если
нужен композит «картинка + развёртка» (для отчёта), это отдельная функция: grab обоих
виджетов (или области главного окна) — обе поверхности уже безопасны.

**Презентер** зеркалирует только `ViewerWidget`, полоса M-mode в него не попадает.

### 4.5 Производительность

Прямоугольник — одна запись в numpy-срез: при 884×1180 и 11 % это ~113 тыс. пикселей,
десятки микросекунд на кадр. Воспроизведение и экспорт не замедляются.

## 7. Приватные теги: итог после проверки

Утверждение v1 («GE держит глубину/пресет в `0x7FE1`, поэтому приватные удалять нельзя»)
**опровергнуто дважды**:

1. Поиск по всем **245 файлам**: группа `0x7FE1` — **0 вхождений**. У GE есть только
   `0x6003`. Следовательно `get_gems_movie_group()`, `get_depth_cm()`, `get_scan_preset()`
   (`ge.py:298,312,336`) на этих данных не получают ничего.
2. Эти методы **не вызываются нигде** в репозитории (src, tests, bench, scripts) —
   мёртвый код. PrivateCreator из `0x6003`/`0x7FE1` используется только как фолбэк
   определения вендора в `ge.py:matches_dataset()`, при неудаче по стандартному
   `Manufacturer` (0008,0070), который сохраняется.

По вендорам:

| Вендор | Приватные блоки | Дубли идентификаторов |
|---|---|---|
| Samsung | **отсутствуют** (`priv=[]` у всех 201 файла) | негде; реальный дубль — в пикселях |
| Philips | `2001`, `200D` есть | нет (совпадения только с датами внутри UID) |
| GE | `0x6003` есть | **да** — `OtherPatientIDs`, но это стандартный тег (§3.2) |

**Решение:** чистка приватных — опция, по умолчанию OFF. Мотив не «сломаем калибровку»
(это не подтвердилось), а минимальное вмешательство: у Samsung чистить нечего, у Philips
дублей нет, а у ценного `0x6003` риск только потенциальный. Проверять результат будем не
запретом, а сканом (§8).

## 8. Проверка результата — три слоя

**Ключевая поправка.** Substring-тест из v2 (§8.3) **не ловит основную утечку**:
проверено на `Samsung/17.dcm` — строки `ЖЕЛНОВА` и `27-11-2025-0003` в `PixelData`
отсутствуют (`in PixelData = False`), потому что выжженный текст существует только как
набор пикселей-глифов, а не как байты строки. Тест остаётся полезным для тегов и
приватных блоков, но для пикселей нужен отдельный механизм.

| Слой | Что ловит | Как |
|---|---|---|
| **1. Теги и байты** | PHI в тегах, приватных блоках, имени файла, метаданных MP4 | Поиск строк-идентификаторов из исходника в байтах результата. Автоматически, в CI на синтетике, локально на корпусе |
| **2. Структурная проверка пикселей** | «Маска не накрыла» — остались текстовые структуры в полосе | Повторный прогон numpy-детектора текста по замаскированной полосе: если структуры остались — тревога. Без PHI в репозитории, без OCR |
| **3. Визуальный эталон** | Всё, что пропустят слои 1–2 | Ручной контроль на корпусе по чек-листу (уже делается); при необходимости — кроп-эталоны, которые в репозиторий не коммитятся |

OCR-верификатор (прочитать полосу после экспорта и убедиться, что читаемого текста нет) —
возможный четвёртый слой, офлайн-батч. В путь загрузки не входит, добавляется последним.

## 9. Экспериментальная функция (до оценки прогонов)

Детектор и/или верификатор вводятся за флагом настроек, чтобы собрать статистику, не
обязывая пользователя. Что логируем (без PHI — только геометрия):

```text
(vendor, H, W, has_regions, min_panel_y,
 detected_band=(y0,y1,x0,x1), confidence,
 applied_band, profile_band, user_action ∈ {принял, подвинул, отключил})
```

Критерии оценки после прогонов:

1. **Доля файлов, где профиль и детектор расходятся** — если < 5 %, профилей достаточно
   и детектор в продакшене не нужен.
2. **Доля файлов, где детектор нашёл текст вне профильной полосы** — это и есть искомые
   аномалии; оцениваем, PHI это или UI.
3. **Ложные срабатывания на классах `preserve_ui`** (668×1280) — если детектор стабильно
   «находит» UI анализа, правило §4.3 подтверждено и авто-расширение там запрещено
   окончательно.
4. **Время на файл** — подтверждает или опровергает оценку «единицы миллисекунд».
