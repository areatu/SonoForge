## 1. Зачем это было

До 2026-09-06 проигрывание 1280×720 клипов «плыло»: на 30 FPS-клипе доходило до
**11.9 FPS** и до 100 % тиков, опоздавших больше чем в 1.5 раза. Замеры в
`tests/bench/` этого не видели, потому что гоняли `FrameCache` на синтетических
кадрах 16×16…512×512 без Qt, без декодера и без вьюера. Дефекты существовали
только там, где встречаются настоящий `AppController`, настоящий `ViewerWidget`
и настоящий многокадровый DICOM.

## 2. Методика

Измерительный комплект — [`bench/cine720/`](../../bench/cine720/README_RU.md): он
гоняет штатный `AppController` + `ViewerWidget` в живом event-loop Qt
(`QT_QPA_PLATFORM=offscreen`, 1280×720, `FrameTime = 33 мс`), продуктовый код
меняется только monkey-patch'ем прототипов фиксов.

Фикстуры генерируются локально и не коммитятся:

| Вариант | Transfer Syntax | Размер (60 / 120 кадров) | Кадр в ОЗУ |
|---|---|---|---|
| `rgb_raw` | Explicit VR LE, RGB 8-bit | 165.9 / 331.8 МБ | 2.76 МБ |
| `mono_raw` | Explicit VR LE, MONOCHROME2 16-bit | 110.6 МБ | 1.84 МБ |
| `jpeg` | JPEG Baseline `1.2.840.10008.1.2.4.50` | 6.29 / 12.58 МБ | 2.76 МБ |

Скрипты: `bench_decode.py`, `bench_prefetch.py`, `bench_playback_e2e.py`,
`bench_playback_fixes.py`, `bench_scroll.py`, `bench_render.py`, `bench_cpu.py`.

## 3. Находки

Четыре P0-дефекта, вместе стоившие **25 из 30 FPS**.

### 3.1. Сессия DICOM жила в `threading.local()` — и не жила вовсе

Сессии кешировались в `threading.local()`, но пул-потоки PySide6 созданы не
модулем `threading`: `QRunnable.run()` входит с `PyGILState_Ensure` и выходит с
`PyGILState_Release`, а это уничтожает thread state вместе со всеми
thread-local значениями. Каждый вызов воркера строил новую сессию и перечитывал
файл целиком.

Измерено на 1280×720: **184–219 мс на батч из 2–8 кадров**, из которых ~16 мс —
собственно декодирование; **192–638 мс на шаг скролла**; пик RSS **~1 ГБ на один
332 МБ cine** (файл читался в память, а затем пиксельный блок копировался из
него ещё раз).

Что сделано: одна сессия на разрешённый путь, общая для всех потоков и
сериализованная `RLock`; пиксельный блок несжатых клипов не копируется, а
отображается через `np.memmap`; `release_heavy()` не вызывается на каждом батче.
Тот же дефект был у MP4-читалки (`cv2.VideoCapture` переоткрывался и заново
строил индекс ключевых кадров, до 60 seek+read проб на батч) — читалки тоже стали
общими на путь с блокировкой.

Закреплено:

- [`tests/unit/test_session_registry.py`](../../tests/unit/test_session_registry.py) — одна
  сессия на путь, общая между потоками, повторное открытие после `release()`;
- [`tests/unit/test_worker_frame_loader.py`](../../tests/unit/test_worker_frame_loader.py) —
  `release_heavy()` не вызывается на батче (иначе декод снова читает файл);
- [`tests/bench/test_cine_playback_e2e_ci.py`](../../tests/bench/test_cine_playback_e2e_ci.py) —
  сквозное проигрывание без «cache miss».

### 3.2. Кеш уровней отображения никогда не попадал

`display levels` пересчитывались на каждый кадр, хотя окно/уровень не менялись:
кеш сравнивал вновь посчитанное значение вместо входа, поэтому промахивался
всегда. Закреплено бюджетами `render` в e2e-гейте.

### 3.3. Период таймера игнорировал работу собственного тика

Таймер проигрывания отмерял фиксированный интервал и не учитывал, сколько занял
сам тик: кадры «догоняли» друг друга, интервалы разъезжались (p95 84.5 мс на
mono8 против 33.3 мс у здорового дерева). Исправлено пейсингом от `FrameTime`
минус фактическая стоимость тика.

### 3.4. ROI пересчитывался на каждый кадр

Пересчёт области интереса на каждый кадр стоил **23.93 мс** на кадр
(`show_frame_fast` против 0.57 мс после фикса) — на mono8 это был главный
съедатель бюджета. ROI стал пересчитываться при смене геометрии, а не кадра.

## 4. Результаты

### 4.1. До и после

Машина аудита: 2 vCPU / 4 ГБ, Debian 12, offscreen raster. «Сломано» — коммит
`cf82a7b` (до фиксов), «исправлено» — дерево на момент закрепления гейта.
Числа живут в docstring e2e-теста и перепроверяются его порогами.

```
                            fixed tree              cf82a7b (broken)
mono8 720p, 60 frames       30.92 FPS               11.91 FPS
  p95 inter-frame gap       33.3 ms                 84.5 ms
  ticks overdue >1.5x       0 %                     100 %
  render (show_frame_fast)  0.57 ms                 23.93 ms
  Play -> first frame       59 ms                   195 ms
RGB24 720p, 30 frames       30.71 FPS                8.75 FPS
  p95 inter-frame gap       34.5 ms                 129.6 ms
  ticks overdue >1.5x       0 %                     100 %
  render (show_frame_fast)  1.06 ms                  2.91 ms
  Play -> first frame       38 ms                   186 ms
cache misses                0 % both                0 % both
```

### 4.2. Память

Один 332 МБ cine больше не занимает RSS ~1 ГБ: файл не читается целиком, а
отображается `np.memmap`, и декодируются только запрошенные кадры.

### 4.3. Стоимость прогона в CI

E2E-проигрывание требует настоящего `QApplication`, декодера и 4 секунд
реального времени на измерение, поэтому в обязательный граф PR он не входит:
это `tests/bench/`-набор (маркер `gui`), который гоняется отдельно, а не в
блоках `test-logic`/`test-gui`. Отсюда — требование к спекам о времени прогона:
падать должны дешёвые инварианты (`test_session_registry`,
`test_worker_frame_loader`), а сам e2e-бенч служит доказательством, а не
постоянным гейтом на каждом PR.

## 6. Как воспроизвести

```bash
# 1. фикстуры (сотни МБ, не коммитятся)
python bench/cine720/gen_cine720.py "" 60 rgb_raw,mono_raw,jpeg
python bench/cine720/gen_cine720.py "" 120 rgb_raw,jpeg

# 2. сквозной прогон в штатной конфигурации
QT_QPA_PLATFORM=offscreen python bench/cine720/bench_playback_e2e.py <file>

# 3. обязательный e2e-гейт
uv run pytest tests/bench/test_cine_playback_e2e_ci.py -v
```
