# Диагностика памяти и очередей для #553 / #545

Инструмент `scripts/memory_queue_probe.py` запускает обычное приложение из
исходников и отдельную панель ручных отметок. Запись **выключена по умолчанию**:
при обычном запуске SonoForge ничего не меняется. Это исследовательский probe,
а не ограничитель памяти, средство измерения input-to-display latency или
замена нативной приёмке.

## Подготовка и запуск

Используйте тестовый профиль и обезличенные исследования, разрешённые для теста.
Запуск открывает обычное приложение с его настройками и persistence: он не
изолирует профиль, не отключает автосохранение и может восстановить последнюю
сессию. Не выполняйте испытания на рабочем клиническом профиле. Установите
проект с зависимостями в виртуальное окружение (`pip install -e .`), как для
обычного запуска из исходников. Нужны нативные GUI-зависимости; offscreen/stubs
пригодны только для технической проверки инструмента. Инструмент не запускает и
не подключается к уже запущенной packaged-сборке.

Из корня репозитория (создайте каталог заранее):

```bash
mkdir -p bench/reports
.venv/bin/python scripts/memory_queue_probe.py --output bench/reports/memory-run-01.jsonl
```

Windows PowerShell:

```powershell
New-Item -ItemType Directory -Force bench/reports
.venv\Scripts\python.exe scripts/memory_queue_probe.py --output bench/reports/memory-run-01.jsonl
```

`--interval-ms 1000` меняет период (250–5000 мс, по умолчанию 500). Каждый
запуск требует **новое имя файла**: существующий файл или ссылка не
перезаписывается. Отчёты в `bench/reports/` исключены из Git. Файл создаётся с
режимом 0600 на POSIX; на Windows используйте защищённый каталог с подходящими
ACL. Не добавляйте персональные данные в имя файла. Перед передачей отчёта
проверьте содержимое и политику организации; даже обезличенные метрики могут
раскрывать характеристики рабочего процесса.

## Прогон

1. Дождитесь открытия приложения и панели `Memory / queue markers`.
2. Нажмите соответствующую кнопку **непосредственно перед** действием и кнопку
   окончания сразу после него: playback, scrub, переключение вкладок,
   сравнение. Для анализа отметьте старт и фактическое действие отмены.
3. Выполните повторные циклы и нажмите `Idle / waiting` в одной и той же точке
   каждого цикла, после согласованной паузы. Метка не доказывает, что workers
   завершились; это проверяется отдельно.
4. Закройте приложение обычным способом. Последняя строка `end` означает, что
   recorder корректно закрылся. Без неё запись неполная (например, аварийный
   выход, ошибка записи или лимит 25 MiB). При ошибке панель предупреждает,
   запись останавливается; stderr не содержит текст исключения.
5. Отдельно зафиксируйте commit, ОС, RAM, настройки и обезличенные характеристики
   данных. Такие сведения и измерения latency сами в JSONL не попадают.

## Поля и интерпретация

JSONL содержит header с версией формата и периодом, затем timestamp
`elapsed_s` от монотонного времени и samples. Метки — только фиксированный
набор кнопок; произвольный текст не записывается.

- `process.rss_bytes`: RSS/working set главного процесса; `children_rss_bytes`
  — сумма доступных дочерних процессов на момент замера. Это не уникальная
  физическая память: страницы могут разделяться. `children_complete=false`
  означает неполные данные или неудачное перечисление, `null` — недоступно.
  `true` означает только отсутствие обнаруженной ошибки при этом замере, не
  гарантию полноты дерева процессов. Короткоживущие процессы между пробами
  могут быть пропущены.
- `cache`: только активный `FrameCache`: логические, owned и pinned bytes,
  текущий budget, число кадров, режим и его собственный high-water mark.
  Это не все кеши и не общая память приложения. Пик кеша может сбрасываться при
  его очистке; он не равен пику RSS.
- `comparison`: учётные reservations двух панелей и их локальный cap, не
  измерение всех выделений сравнения. `null` cap означает отсутствие лимита.
- `queue`: только parked-работа данного `DecodeGate`. `estimated_pending_bytes`
  — оценка работы, **не RSS и не выделенные пиксели**; dropped — счётчик с
  момента создания gate. Активные задания, ожидающие вне gate задачи пула,
  декодеры и MP4 этим не охватываются.

GUI-поток выполняет пробы, поэтому при блокировке интерфейса они задерживаются;
могут пропускаться короткие пики. Частота и сбор статистики сами создают
нагрузку. Для независимого peak RSS и диагностики зависшего UI используйте
внешний монитор процесса; для кадровой latency и проверки визуальной
корректности нужны отдельные измерения. Снимки не доказывают утечку, общий
жёсткий бюджет, отмену native codec или валидность клинических результатов.
