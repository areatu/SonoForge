## Задачи и пункты исходной заявки

### 1. Меню названия по правой кнопке (п. 1)

После установки точек калипера или контура из Общих инструментов
(площадь, объём) ПКМ по точке открывает меню с выбором уточнённого
(каталожного) или произвольного названия. Название со значением
переносится в отчёт (сепарация перикарда, размер образования,
толщина створки и т.п.).

- Точка попадания: hit-test в экранных пикселях (радиус 14 px),
  ближайшая точка побеждает (конец калипера `start`/`end`,
  узел контура `points`).
- Калиперы: только переименовываемые — generic `Dist*` и уже
  кастомные; фиксированные ярлыки инструментов (LVEDD, TAPSE,
  Ao Sinus, %D стеноз, S1, ORGAN-VOL-1 …) не трогаем
  (`is_renamable_caliper_label`, `ANATOMICAL_CALIPER_LABELS`).
- Контуры: только generic area/volume (`GENERIC_AREA_CHAMBER`,
  `GENERIC_VOLUME_CHAMBER`).
- Меню — существующий `LabelPicker`; новое: `allow_free_text` для
  любого контекста (раньше свободный текст жил только в planimeter).
- Приоритет ПКМ: точка → (пропуск) радиальное меню → save-меню.
  Во время рисования (контур, freehand, половина отрезка, калибровка)
  ПКМ ничего не открывает.
- Прокачка кастомного названия калипера в отчёт уже работала
  (`caliper_label` отдаёт raw, `measurement_for_caliper` →
  `caliper.length`); страховочный тест в `test_report_builder`.

### 2. Выбор при нескольких измерениях (п. 2)

При нескольких измерениях (или парах: ЛЖ-диастола → КСР ЛЖ,
КДО 4-кам → КСО 4-кам) отчёт предлагает выбор. Без выбора —
результат последнего (хронологически) измерения.

- Domain: кандидаты-дубли одного показателя в `MeasurementSnapshot` /
  `build_report_groups`; дефолт = последний.
- Хронология: порядок вставки в `linear_measurements`
  (`merge_newest_wins` его сохраняет). Если ревью покажет, что
  порядок не гарантирован после reload — schema v8 + поле времени
  (дороже; решить на PR-B).
- UI: маленький диалог/сегмент-выбор у строки отчёта (или в карточке
  «откуда значение»); выбор живёт на вкладке.

### 3. Диаметр НПВ и ДПЖ (п. 3)

Линейное измерение «диаметр нижней полой вены» (НПВ) в ПЖ/ПП-секции,
активно в 2D и M-режиме. В M-режиме — два показателя: «НПВ выдох»,
«НПВ вдох». Из них считается давление в правом предсердии (ДПЖ/RAP)
для калькулятора и отчёта.

- Каталог: `ivc.d` (2D), `ivc.d_exp`/`ivc.d_insp` (M-mode pair);
  caliper-ярлыки `IVC`, `IVC-EXP`, `IVC-INSP` в `CALIPER_TO_MEASUREMENT`
  и `_LABEL_I18N_KEY`.
- Расчёт: `domain/calculations/right_atrial_pressure.py`:
  `ivc_collapse_percent(exp, insp)`, `rap_from_ivc(diameter_cm, collapse)`
  по ASE (3 / 8 / 15 мм рт.ст.), `rap_from_ivc_pair(exp_mm, insp_mm)`.
- Калькулятор: авто-подстановка расчётного RAP в input `rap`
  (`calculator_inputs.py`, сейчас `manual_only` — снимаем флаг или
  добавляем ветку резолвера с приоритетом ручного ввода).
- Отчёт: строки НПВ (автоматически через `_append_linear_report_values`)
  + производная строка ДПЖ в GROUP_RIGHT_ATRIUM; нормы из
  `ivc_diameter` (≤21 мм) справочника.
- Кнопки: `menu.ra_group` (НПВ 2D) + `menu.mmode_group`
  (НПВ выдох/вдох), `MeasurementAction.IVC_*`, хендлеры в `main_window`
  (для M-mode — по образцу `_on_rv_tapse` с проверкой готовности
  M-режима), вертикальные ярлыки `_vertical_caliper_labels`.

### 4. Включение/исключение показателей отчёта (п. 4)

Не все показатели должны печататься (длина ЛЖ, УО по Тейхольцу,
Vmax ВТЛЖ и др.). Пользователь убирает/добавляет показатели —
чек-боксы на белом листе или диалог; выбор сохраняется для
дальнейших исследований (шаг к профилям пользователей).

- База уже есть: скрытие строк `report_hidden_values` на вкладке
  (`tab_session.py:80`), меню «скрыть» на ячейке
  (`report_mode/preview.py:712`), «Скрытые» в левой колонке
  (`report_coordinator.py:617`), `build_report_document(hidden_keys=…)`.
  Но набор не переживает исследование.
- UI: **диалог**, не чек-боксы на листе (лист — точные PDF-байты,
  `preview.py:715`; правки на нём ломают печать). Быстрое «скрыть»
  на ячейке остаётся.
- Персистентность: JSON-предпочтение в `preferences_contract.py`
  (`ReportFormatPreferences`): `report_value_excluded`, дефолтный
  набор скрытых производных строк — таблицей в domain.
- Ключи строк — существующие `ReportValue.key = group:label:ordinal`.

### 5. Сортировка/перемещение показателей (п. 5)

Порядок показателей в отчёте меняется пользователем — через тот же
диалог выбора показателей (п. 4).

- `report_value_order` (list ключей) в том же предпочтении.
- Применение: `build_report_groups` — порядок внутри группы по
  сохранённому order; `GROUP_ORDER` (`report_groups.py:42`) остаётся
  дефолтом для групп.
- UI: move up/down или drag в диалоге из п. 4.

### 6. Автоматическое заключение (п. 6)

Формализованные фразы по результатам измерений: аорта в норме →
«Аорта не расширена»; расширение ЛП по иОЛП → «Дилатация левого
предсердия»; степени регургитаций/стенозов. При неоднозначной
градации (MR 2 или 3) — диалог выбора одной. Часть фраз уже есть
в библиотеке (`report_phrases.py`: «Корень и восходящий отдел аорты
не расширены», `report_conclusion.py`: «Глобальная систолическая
функция ЛЖ сохранена»).

- Domain-находки в `domain/services/report_conclusion.py`:
  аорта по нормам (sinus/STJ/asc), ЛП по иОЛП/диаметру (база —
  `la.size` по биплановому LAVi), градации MR/MS/AR/TR из
  `regurgitation_grade.py`/`mitral_stenosis.py`.
- Неоднозначные градации: находка возвращает список кандидатов;
  UI-диалог по образцу `ChecklistDecisionDialog`
  (`report_mode/checklist_decision.py`); выбор живёт на вкладке,
  вставка в managed-блок заключения (`merge_conclusion`).
- Локали фраз ru/en; синхронизация с `report_phrases.py`
  (не дублировать существующие).
- Зависимость: после PR-A (ДПЖ/RVSP могут войти в заключение).

### 7. LVMi в отчёте (п. 7)

`LVMi` в отчёте печатался без перевода (иММЛЖ) — исправлено в PR-A
коммитом `fix(report): translate LVMi row label`:
`report_builder` берёт подпись из каталога
(`_label_catalog("lv.mass_i")`), ключ нормы остаётся `LVMI`.

### Проверка перед PR

- `uv run ruff check` по изменённым файлам;
- `uv run pytest` точечно по тематическим файлам;
- если менялся набор тестов:
  `uv run python .github/scripts/update_pytest_baseline.py --fix`
  в том же коммите, перед пушем `--check`;
- rebase на `main` и проверка конфликтов перед созданием PR
  (workflow гоняется долго, merge-конфликты ловить заранее).
