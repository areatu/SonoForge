# Спайк UI-4.0 — предпросмотр отчёта: `QPdfView` или свой раскладчик

**Дата:** 2026-10-19

**Статус:** Завершён. **Решение: путь (а)** — лист A4 в режиме «Отчёт» показывает
байты PDF из `measurement_report_pdf.render_report` через `QPdfDocument` +
`QPdfView`; «откуда значение» работает по координатам ячеек значений,
записанным при сборке PDF. Путь (б) (общий раскладчик для QPainter и reportlab)
не нужен.

**Вопрос:** §4.6 спеки редизайна — предпросмотр строится из `ReportDocument`
«как PDF»; путь выбирается этим спайком: (а) показывать байты PDF через
`QPdfDocument`/`QPdfView` (модули `QtPdf`/`QtPdfWidgets` — проверить на версии
из `uv.lock`) с записью координат ячеек значений при сборке, либо (б) писать
общий раскладчик страницы для QPainter и reportlab. Условие выбора (а) —
пересборка укладывается в 500 мс после изменения значения (с дребезгом).

**Проверочная база:** ветка `arena/9ee7e8d6-sonoforge` @ `0d29ba5` плюс
`render_report` (контракт §8.4), закреплённый этим же изменением; PySide6
**6.11.1** из `uv.lock`; Linux-контейнер без системного OpenGL — Qt запускался на
заглушках `tools/qtstub` (это ограничение песочницы, не продукта). Скрипты
спайка — `tools/report_preview_spike/`.

> Это не клиническая валидация и не приёмка UI-4: спайк отвечает на технический
> вопрос «можно ли строить предпросмотр тем же рендером, что и PDF, и попадать
> курсором в ячейки значений».

---

## 1. Короткий ответ

**Да, путь (а) работает и укладывается в бюджет.**

1. `QtPdf` и `QtPdfWidgets` есть в PySide6 6.11.1 из `uv.lock`; бинарники лежат
   в `pyside6-addons`, который мета-пакет `pyside6` тянет автоматически.
2. Пересборка: типичный отчёт (80 значений, 3 страницы) — **52 мс p50 / 55 мс
   p95** (render + load), крупный (250 значений, 8 страниц) — **151 мс p95**.
   Бюджет 500 мс выполняется с трёхкратным запасом даже для крупного; с
   дребезгом 300 мс пересборки не заметно.
3. `QPdfView` не отдаёт геометрию страницы наружу, но его раскладка полностью
   воспроизводима: модель `tools/report_preview_spike/view_map.py` (списана с
   `QPdfViewPrivate::calculateDocumentLayout`, Qt 6.11) сошлась с пикселями
   в 13 конфигурациях (2 размера × 3 режима зума × single/multi + скролл):
   **51/51 хиттестов в нужную ячейку**, худшее расхождение прямоугольника
   **1.86 px** (квантование краёв растра, не ошибка модели).
4. Link-аннотации в PDF не нужны: якоря `render_report` + модель геометрии
   покрывают наведение, и экспорт остаётся чистым PDF без невидимых ссылок.

## 3. Бюджет пересборки ≤ 500 мс (условие пути (а))

`tools/report_preview_spike/render_bench.py`, 25 итераций, Linux-контейнер
(заглушки Qt на CPU):

| Сценарий | Значений / страниц | `render_report` p50 / p95 | `QPdfDocument.load` p50 / p95 | Растр стр. 1 (~150 dpi) p50 / p95 | Пересборка p95 | ≤ 500 мс |
|---|---|---|---|---|---|---|
| small (2×4) | 8 / 1 | 15,4 / 20,5 мс | 0,2 / 0,3 мс | 4,2 / 6,1 мс | **20,8 мс** | да |
| typical (10×8) | 80 / 3 | 51,6 / 54,6 мс | 0,3 / 0,4 мс | 5,5 / 5,9 мс | **55,0 мс** | да |
| large (25×10 + заключение) | 250 / 8 | 134,9 / 150,4 мс | 0,3 / 0,4 мс | 5,4 / 5,8 мс | **150,9 мс** | да |

«Пересборка» = `render_report` + `load` (то, что блокирует UI при правке
значения). Растер страницы `QPdfView` делает на своём потоке и не блокирует
интерфейс; в бюджет его не включаем, но он и так ~5 мс. Вывод: пересборку можно
делать синхронно после дребезга 300 мс, отдельный воркер не нужен. На Windows
замер повторить (см. §7).

## 4. Геометрия `QPdfView` и «откуда значение»

### 4.1. Что нельзя использовать

- **`QPdfPageNavigator.currentZoom()` / `currentLocation()`** — не отражают
  трансформацию вьюера: возвращают `1.0` и `(0,0)` независимо от зума и
  скролла (это состояние «последнего jump()», а не экрана).
- **`QPdfView::zoomFactor` в документации** описан как «пиксель = пункт», но в
  коде масштаб страницы = `zoomFactor × logicalDPI/72`. При 96 dpi 1.0 →
  4/3 px/pt; на Windows при 150 % (logicalDPI 144) — 2.0 px/pt. Кнопка «100 %»
  в UI-4 должна исходить из этого, а не из названия.

### 4.2. Модель, которая сошлась с пикселями

Исходник: [`qtwebengine/src/pdfwidgets/qpdfview.cpp` @ 6.11](https://raw.githubusercontent.com/qt/qtwebengine/6.11/src/pdfwidgets/qpdfview.cpp)
(приватный `QPdfViewPrivate::calculateDocumentLayout` и
`screenScaleTransform`). Правила, которые воспроизводит `view_map.py`:

- «100 %» страницы: `page100_px = round(pt × screenResolution)`, где
  `screenResolution = logicalDPI / 72` — значение Qt **запоминает один раз при
  создании вьюера** (даже если потом окно переедет на экран с другим DPI);
- `Custom`: `page_px = round(pt × screenResolution × zoomFactor)`;
- `FitToWidth`: `pageScale = (viewport_w − ml − mr) / page100_px.w`;
- `FitInView`: страница вписывается в
  `(viewport_w − ml − mr) × (viewport_h − pageSpacing)` — **высота считается с
  вычетом межстраничного интервала, а не маржинов**. Отсюда аномалия «наивной»
  модели: вписать по высоте получается примерно на 1 % крупнее, чем
  `(viewport_h − ml − mr)/page_h`. Это не баг спайка, а формула Qt;
- страница центрируется по горизонтали:
  `page_x = (max(totalWidth, viewport_w) − page_px.w) // 2` (маржины входят в
  `totalWidth`, но не в центрирование); по верху — всегда маржин;
- мышь → пункты страницы: `(pos + scroll − origin_page) / scale` — то же
  выражение, которым `QPdfView::mouseMoveEvent` ходит в `QPdfLinkModel.linkAt`.

### 4.3. Пиксельная проверка

`tools/report_preview_spike/hover_probe.py`: PDF с шестью чёрными маркерами с
известными координатами (каждый маркер сам записывает, где он нарисован) →
`QPdfView` в 13 конфигурациях → grab → сравнение bbox маркера с моделью →
хиттест-раундтрип в центр маркера.

| Проверка | Результат |
|---|---|
| Конфигурации | 600×800 и 1000×1200; FitToWidth / FitInView / Custom 1.0 / Custom 0.5; SinglePage / MultiPage; скролл 120 px |
| Хиттест «курсор → ячейка» | **51 из 51** в правильную ячейку |
| Худшее расхождение прямоугольника | **1.86 px** (FitInView 1000×1200; у остальных ≤ 1.7 px) — половина краевого пикселя на каждом краю, квантование растра |
| Первый paint после смены документа | 390–2000 мс в контейнере — `QPdfView` рендерит страницы на рабочем потоке (кэш 20 страниц) и перерисовывается по готовности; пустой первый кадр — норма, не ошибка |

Вывод: для хватания ячеек курсором точности хватает с запасом (допуск хиттеста
3–4 пункта ≈ 4–5 px). Модель чистая функция — годится для юнит-тестов в UI-4.

### 4.4. Link-аннотации не нужны

`QPdfLinkModel.linkAt` принимает пункты — можно было бы вшивать в PDF невидимые
ссылки и хиттеститься через Qt. Не делаем: якоря `render_report` покрывают те же
ячейки, модель геометрии одна, а в экспортированном PDF не появляется
посторонних объектов (важно для чистого документа и golden-тестов UI-4).

## 5. Контракт §8.4, закреплённый кодом

`echo_personal_tool.infrastructure.measurement_report_pdf`:

```python
render_report(document: ReportDocument, *, font_size: int = 10) -> RenderedReport
# RenderedReport(pdf: bytes, anchors: dict[ValueId, list[PageRect]])
# PageRect(page, x, y, w, h) — пункты, начало координат — верхний левый угол
# ValueId = (group_index, value_index) в ReportDocument
```

- Ячейка значения рисуется `_AnchoredParagraph` (наследник `Paragraph`):
  координата снимается в `drawOn` из `canv.absolutePosition` — один проход,
  запись физически не может разойтись с нарисованным PDF.
- Координаты — пункты, **верх-лево, y вниз**: пространство растеризации
  (`QPdfDocument.render`, `QPdfPageRenderer`), окно предпросмотра не пересчитывает
  ось.
- `list[PageRect]` на значение — на случай переноса/повтора строки.
- `export_report_document_pdf` = `render_report` + атомарная запись байтов:
  предпросмотр и экспорт не могут разойтись (S-11). Ошибки — тот же
  `PdfExportError`.
- **`ValueId` пока позиционный**: у `ReportValue` нет стабильного id. В UI-4
  PR-4 («откуда значение») ховер получает `ValueId` → `ReportValue` из того же
  документа → происхождение из QH-1b (`result_id`); где происхождения нет —
  «происхождение не записано», статус `unverified` (QH §5.3), без догадок.
- Тесты: `tests/unit/test_report_render.py` (10 логических) — состав якорей,
  границы страниц, порядок строк, многостраничный документ, ошибки →
  `PdfExportError`, и перекрёстная проверка с fitz: глифы значения лежат внутри
  записанного прямоугольника. Существующие тесты экспорта не менялись и зелёные.

## 6. Рекомендации UI-4 (PR-1…PR-5)

| Тема | Рекомендация |
|---|---|
| Предпросмотр (PR-1) | `QPdfView` + `render_report`; MultiPage + FitToWidth как режим по умолчанию (лист A4 во всю ширину колонки); дребезг 300 мс, пересборка синхронная (бюджет §3) |
| Ховер (PR-4) | event filter на `viewport`, геометрия — `view_map.py` (перенести в `presentation/report_mode/` как чистую функцию + юнит-тесты); допуск 3–4 пункта; карточка «откуда значение» — содержимое из provenance |
| Маркеры «измерить» (PR-2) | отдельный слой поверх вьюера, не в PDF (спека §4.6); ячейка всё равно имеет координаты из якорей |
| Зум | любой из трёх режимов модель покрывает; «100 %» считать как `screenResolution` (§4.1), не как 1 px/pt |
| Hi-DPI / мультимониторность | `screenResolution` фиксируется при создании `QPdfView` — модель брать то же значение; проверить Windows 10/11 при 100/150/200 % в чек-листе UI-4 |
| PyInstaller | `hiddenimports` += `PySide6.QtPdf`, `PySide6.QtPdfWidgets`; проверить предпросмотр в Windows-сборке |
| Golden-тесты UI-4 | текст экрана и PDF — из одних байтов (fitz-извлечение, как в `test_report_render`); RU и EN; маркеры «измерить» не печатаются |
| Смена документа | первый paint асинхронный — после `load` не считать пустой кадр ошибкой; при UQ-07 «Завершить» пересборка та же |

## 7. Риски и открытые места

| Риск | Мера |
|---|---|
| Qt 6.12+ изменит раскладку `QPdfView` (у нас pin `<6.12`) | `hover_probe.py` — быстрая перепроверка при обновлении Qt; модель рядом с тестами UI-4 |
| Windows hi-DPI: `logicalDPI/72` вдвое меняет масштаб «100 %» | чек-лист UI-4: 100/150/200 %, два монитора с разным DPI |
| Первый paint до ~2 с в контейнере при больших листах | измерить на Windows; если заметно — прогревать рендер после смены документа |
| `ValueId` позиционный | PR-4 привязывает к provenance; до тех пор ховер работает по документу в памяти |
| Производительность на слабых машинах | запас бюджета трёхкратный; повторить `render_bench.py` на целевой машине |
