# Аудит длительности CI — 2026-11-21

## Вывод

Основной критический путь — выполнение `tests/unit/ -m 'not gui and not interactive'`,
а не установка зависимостей и не последовательный запуск платформ. Logic уже выполняется
параллельно через xdist, а пять OS/Python-ячеек запускаются параллельно друг другу.
Простая перестановка jobs не вернёт 12–15 минут. Приоритет: измерить накладные расходы
fixtures, отделить Qt от действительно чистых тестов, затем разбить оставшийся длинный
logic-контур на сбалансированные shards.

Workflows и тесты в ходе этого аудита не изменялись. Ранее внесённые исправления CI сохранены.

## 2. Главный кандидат: Qt-hygiene применяется и к чистой логике

`tests/unit/conftest.py:36–48`: `_unit_qt_environment` — autouse для каждого unit-теста,
кроме отдельного `--pure-core` запуска. Маркер `not gui` эту fixture не выключает.
Через неё выполняются:

- `_gc_per_test` (`:136–147`): отключение GC на время теста и полный `gc.collect()` после;
- `_isolate_user_settings` → `isolated_qsettings` (`:462–493`): отдельное хранилище,
  `clear()` и `sync()` в setup и teardown;
- `_drain_global_thread_pool` (`:78–93`): `QThreadPool.globalInstance().waitForDone(5000)`;
- восстановление общей таблицы стилей;
- подмена WebEngine.

Дополнительно `tests/conftest.py:20–43` доставляет Qt DeferredDelete и обрабатывает события
после каждого теста, если существует приложение.

Это подтверждённая лишняя связность для чистых математических/AST/schema-тестов.
Её вклад в 30 минут **пока не измерен**. В частности, `waitForDone(5000)` — верхняя граница,
а не обязательное ожидание 5 секунд: на свободном пуле он возвращается сразу.

Рекомендуемая правка после профилирования: чистый контур без Qt-hygiene; явный Qt-runtime
контур с полной текущей защитой. Изоляцию путей/хранилищ оставить там, где она нужна.
Не выключать cleanup безусловно по `not gui`: ниже показаны Qt-тесты без такого маркера.
Не убирать GC/DeferredDelete из Qt-контура: комментарии и история фиксируют SIGSEGV/OOM,
которые эти меры предотвращают.

## 3. `not gui` сейчас не означает отсутствие Qt

AST-аудит локального дерева обнаружил **48 тестовых функций в 11 файлах**, которые прямо
запрашивают `qapp`, `qtbot` и подобные fixtures, но не имеют явного `gui` на функции,
классе или модуле. Учтён также `pytestmark` внутри классов.
Это нижняя оценка кандидатов: не учтены косвенные fixtures и размножение параметризацией;
это не результат фактической pytest collection.

Явные примеры настоящих виджетных тестов:

- `test_report_template_editor.py`: 14 функций с прямым `qtbot`, создают/показывают редактор;
- `test_viewer_widget_ecg_strip.py`: 10 функций, создают `ViewerWidget`;
- `test_ecg_strip_widget.py`: 8 функций, создают ECG-виджет;
- `test_viewer_widget_loop.py`: минимум 3 прямых обращения к `qtbot`, плюс другие тесты
  через fixture `widget`, создающую `ViewerWidget`;
- `test_viewer_loupe_warmup.py`: 6 функций с прямыми Qt-fixtures.

Эти тесты попадают в пять logic-ячеек, вместо ожидаемого отделения виджетного контура.
Наличие `qapp` само по себе ещё не означает GUI: QObject/PDF-тесты могут обоснованно
относиться к отдельному Qt-runtime контуру, а не к UI smoke.

После ручной классификации добавить guard: виджетный тест без нужной категории не должен
незаметно возвращаться в чистую логику. Guard должен учитывать зависимости fixtures.

Важные ограничения миграции:

1. `check_test_inventory.py` проверяет и `not_gui`; перевод тестов в GUI уменьшит этот
   счётчик. Нужен осмысленный `Test-Inventory-Decrease: ...`, описывающий перенос,
   а не повышение baseline или отключение inventory.
2. Сейчас все эти тесты исполняются на пяти платформа/Python-комбинациях. Простой перевод
   в Linux-only GUI shards уменьшит платформенное покрытие. Чтобы не ослабить проверки,
   сохранить необходимые тесты в выделенных Qt-ячеках тех же комбинаций либо отдельно
   согласовать сокращение платформенной матрицы. Native GUI smoke не эквивалентен полному набору.

## 4. План оптимизации по приоритету

### P0 — один диагностический прогон, без изменения проверяемого набора

- Сохранять все длительности `setup / call / teardown` по nodeid, worker и файлу,
  а не только top-25; отдельно измерить collection и worker idle time.
- Свести top файлов и фаз в GitHub Step Summary: сейчас artifacts уже существуют,
  но при недоступности storage диагностика теряется.
- Измерить отдельно `gc.collect`, QSettings sync, ожидание пула; зафиксировать peak RSS
  и число живых Qt-объектов по worker. Не логировать содержимое настроек/пациентских данных.
- Записать реальное число workers/vCPU. Комментарии workflow упоминают и 2, и 4 CPU;
  нельзя выбирать параллелизм, опираясь только на комментарии.
- Сделать A/B одинакового набора с coverage и без него на одном Python.

### P1 — убрать лишнюю работу, не убирать тесты

- Исправить классификацию UI/Qt-тестов; отделить pure logic от Qt-runtime.
- В чистом контуре не запускать Qt cleanup, QSettings и полный GC после каждого теста.
- GUI/Qt cleanup сохранить; явно проверять отсутствие утечек и worker crashes.
- Для часто повторяемого сканирования одного checkout в ratchet-тестах рассмотреть
  переиспользование неизменного результата в рамках тестового модуля. Тесты сканера
  на изменяемых `tmp_path` не кэшировать. Сначала подтвердить стоимость по timings.
- Проверить `fsync` в `.github/scripts/pytest_current_node.py:19–26`: сейчас он вызывается
  для каждого запуска node. Для диагностики падения процесса обычно достаточно закрытой
  записи/flush; гарантия пережить отключение питания runner не нужна. Стоимость и поведение
  на принудительном завершении проверить отдельно, не удалять запись active node целиком.

### P2 — shards для длинного logic-контура

Если после P1 остаётся длинный pytest, добавить сначала **3 logic shards Linux/3.11**,
потом оценить необходимость шардирования compatibility-ячеек. Разбиение по целым файлам,
веса — сумма setup/call/teardown предыдущих прогонов; новые файлы всегда получают shard.
Для новых файлов без истории — детерминированный fallback с ненулевым весом.

Не копировать слепо нынешнее GUI round-robin: равное число файлов не означает равное время.
Один очень тяжёлый файл остаётся нижней границей длительности при `--dist loadfile`.
Не менять на worksteal/loadscope без проверки зависимостей состояния Qt и порядка тестов.

Обязательная сопутствующая работа:

- сохранить success/failure каждого shard как обязательный результат;
- объединять coverage всех logic shards с шестью GUI shards;
- расширить `verify_pytest_partition.py` с одного logic JSON на несколько;
- проверять не только суммы, но и непересечение/полноту nodeids;
- проверку `.github/required-tests/formulas.txt` выполнять по объединённым outcomes,
  иначе каждый shard ошибочно потребует формулы из других shards;
- обновить regression-тесты workflows, artifact names и aggregate checks;
- не превращать crashed/потерянные/пропущенные тесты в успешный результат.

Шардирование уменьшает wall-clock за счёт дополнительных runner-минут и памяти;
реальную экономию CPU даёт P1. При очередях на runners выигрыш будет меньше расчётного.
Иллюстрация, **не прогноз**: 32 минуты равномерной работы / 3 shards + ~2 минуты inventory
+ ~1 минута coverage ≈ 14 минут, без учёта setup, очередей и дисбаланса.

### P3 — вторичные улучшения workflow

- Inventory сейчас стоит перед всеми тестами: текущая последовательная добавка ~2 минуты.
  Можно запускать независимые тесты параллельно с inventory, но оставить inventory
  обязательным в coverage/финальном gate. Это обмен меньшего wall-clock на лишние затраты
  при красном inventory; не первый источник 30 минут.
- `concurrency.group` содержит SHA. Разные коммиты одной ветки имеют разные группы и
  не отменяют друг друга, несмотря на `cancel-in-progress: true`. Это способно расходовать
  runner capacity на устаревшие прогоны. Нужна отмена старых commits с сохранением защиты
  от позднего rerun старого SHA; не удалять SHA без пересмотра stale-run/capacity-healer guards.
- В `lint` повторяются mypy 3.11 и presentation ratchet, которые уже запускает
  `scripts/typecheck_matrix.sh 3.11`. Можно оставить выполнение в одном обязательном job,
  поправив guard-тесты и aggregate dependency. Экономия небольшая: lint сейчас не критический путь.
- Coverage скачивает 15 artifacts последовательными steps. Групповой download с раздельными
  каталогами и явной проверкой ожидаемого набора уменьшит накладные расходы. Сам coverage job
  на main занимал 1:08, поэтому это не решение 30-минутного logic.
- `pytest.log` выводится только после завершения pytest. Потоковый вывод через `tee`
  улучшит наблюдаемость, но нужно сохранить именно exit code pytest (`PIPESTATUS[0]`/pipefail),
  а не сделать зелёным падение тестов. Сам по себе tee тесты не ускорит.
- Проверить A/B с `OPENBLAS_NUM_THREADS=1`, `OMP_NUM_THREADS=1`, `MKL_NUM_THREADS=1`
  в xdist jobs: вложенные native threads могут конкурировать с workers. Это гипотеза,
  особенно для NumPy/SciPy/OpenCV, а не подтверждённый источник текущей задержки.

## 5. Что не рекомендовано

- Не переносить всю Windows/macOS/Python compatibility-матрицу в nightly лишь ради зелёного PR.
- Не исключать pure-core тесты из coverage logic просто потому, что они уже проходят
  отдельным job: сначала нужны coverage и partition accounting для нового контура.
- Не увеличивать `-n auto` до 8/16 вслепую: CPU/RAM, GC и внутренние BLAS threads могут
  сделать хуже. GUI уже использует 4 workers на shard с историей OOM.
- Не отключать coverage, inventory, required-tests, strict xfail и crash/count guards.
- Не сокращать таймауты как способ «ускорить тесты»: это только раньше оборвёт работу.
- Не начинать с ускорения `uv sync`/apt: в исследованных медленных jobs они занимают секунды.
- Не переставлять чистую логику «перед GUI» в надежде сократить сумму работы. Внутри
  загрязняющегося процесса это может временно помочь, но не устраняет ошибочную изоляцию.

## 6. Остальные workflows

`nightly-suites.yml` уже отделяет deep Hypothesis, mutation, black-box system и живой Orthanc.
Это разумное разделение; не нужно переносить туда обычные обязательные regression-тесты.
`build.yml` и `benchmark.yml` запускаются отдельно от CI и могут конкурировать за capacity,
но не входят как `needs` в исследуемый logic job. `presenter.yml` запускается по тегам/вручную,
поэтому не объясняет обычные 30 минут PR logic.

Практический порядок: **P0 → классификация Qt + P1 → повторный замер → P2 → P3**.
Цель 12–15 минут правдоподобна как инженерная цель, но не обещается без профиля и A/B.

## 7. Первый этап реализации в текущей ветке

После аудита пользователь разрешил изменения. Выбран ограниченный первый этап:
пофазные timings из P0 и файловые shards из P2 на всех пяти прежних OS/Python-ячейках.
Это не меняет рискованную Qt-hygiene и не сокращает платформенный набор тестов.
Первичная балансировка использует число collected items, а не исторические времена:
фактические timings ещё предстоит получить из Actions.

На каждую ячейку добавлены три shard; отдельный `logic_evidence` проверяет точное
непересекающееся покрытие всех logic-nodeids и завершение всех shards. Required-formulas
проверяются после объединения outcomes. Существующий coverage partition verifier
получает объединённый logic JSON и дополнительно проверяет точные nodeids всего Linux-набора.
Coverage сохраняет прежние пороги и получает данные всех трёх logic shards плюс шести GUI.

Локально проверены реальные маленькие pytest-прогоны без xdist и с двумя workers,
отрицательные сценарии потерянных/дублированных результатов и CLI обязательных тестов.
Отдельный smoke с тремя shards и pytest-cov подтвердил JUnit counts и объединение
coverage (100% **синтетического образца**, не всего приложения). Ускорение полного CI
и поведение native Windows/macOS требуют отдельного запуска GitHub Actions.
