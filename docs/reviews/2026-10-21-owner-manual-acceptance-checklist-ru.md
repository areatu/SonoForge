## 0. Как пользоваться листом

Каждый блок содержит четыре части:

1. **Что уже закрыто автоматикой** — специально, чтобы не тратить ручное время на то, что и так проверяется в CI.
2. **Ручная приёмка** — точные действия: сборка → экран → настройка → нажатия → ожидаемый ответ → где снять доказательство.
3. **Вопросы владельцу** — с ID (UQ-…, A-…, G1-STE, …), вариантом по умолчанию и формулировкой «да/нет/иначе».
4. **Куда вернуть ответ** — комментарий в конкретный issue + (для QH) строка в `docs/reviews/`.

### 0.1. Требования к стенду

| № | Требование |
|---|---|
| П1 | **Не checkout.** Сборка из артефакта: Windows — `SonoForge-Setup-<ver>-x64.exe` или portable `.exe`; macOS — `.dmg`; Linux — `.deb`. Либо `gh run view --repo areatu/SonoForge` → артефакт «Build (test artifacts) → sonoforge-windows» (живёт 24 ч) |
| П2 | Разрешения и масштабы: **1366×768 @100 %**, **1920×1080 @100 %**, **1920×1080 @150 %**, плюс (для UA-05) **2560×1440 @150 %** |
| П3 | Локали: **RU и EN** в каждом пункте, где есть текст |
| П4 | Медиа: одно исследование с 3+ клипами (B-mode + допплер + M-mode), один одиночный DICOM-файл, один клип с сохранёнными измерениями, один отчёт с незаполненными разделами |
| П5 | Доказательство: скриншот/видео + строка «PASS / FAIL +Short comment» в указанном issue. FAIL — всегда со снимком и версией сборки |
| П6 | **Платформа:** каждая строка листа помечена меткой [OS:…] / [DUP-all] / [DUP+1] / [ANY-one] — см. §0.2. Строки [DUP-all] без ответа «по всем трём ОС» не считаются принятыми |

### 0.2. Метки объёма по ОС (как читать весь лист)

| Метка | Значение | Что делать |
|---|---|---|
| **[OS:win]** / **[OS:mac]** / **[OS:linux]** | Свойство существует только в этой ОС | Проверить на одной ОС. На остальных фиксировать «н/п» (не применимо), а не «FAIL» |
| **[DUP-all]** | Функция ОС-независима, но уязвима к платформенным отличиям | Прогнать **на всех трёх ОС**, ответы в одном комментарии списком «win / mac / linux» |
| **[DUP+1]** | Обязательных платформ две, третья — по желанию | Минимум две (обычно win + mac); Linux часто закрыт CI-автоматикой, но снимок желателен |
| **[ANY-one]** | Платформа не важна, важна среда/данные/сборка | Один прогон; выбирать **сборку из релиза**, не checkout |

### 0.4. Почему Linux в этом листе выглядит обделённым (и что с этим делать)

**Причина не в том, что Linux менее важен, — в том, где он уже покрыт.**

1. **Linux — первичная CI-платформа.** В `.github/workflows/ci.yml` 11 из 14 джобов идут на `ubuntu-latest` (`test_inventory`, `test_logic`, `test_gui`, `test_bench`, `test_security`, `test_acceptance`, `ui_colors`, `coverage`, `build`, `release`, `push`), и только `test_compat` и `test` разворачиваются матрицей на `macos-latest` / `windows-latest` / `ubuntu-latest`. Ручная часть по специфике сознательно уезжает туда, где автотестов меньше всего.
2. **Автобаза почти вся исполняется на Linux:** 484 файла в `tests/unit`, 10 в `tests/security`, плюс `tests/compat`, `tests/acceptance`, `tests/bench` и `tests/regression`. Это и есть ответ, почему «для Linux проверок мало» — они не ручные, а машинные.
3. **Гейт GUI по QH привязан к Linux/Xvfb** (спека QH, §6.1: «Critical GUI acceptance — Required на Linux/Xvfb»): `test_gui`, `test_acceptance` и `test_bench` идут через `xvfb-run -a` в `ci.yml`. Важная оговорка, из-за которой «мало» превращается в «недостаточно»: Xvfb — это X11-виртуальный дисплей без композитора и без Wayland, а `QT_QPA_PLATFORM=offscreen` не рисует кадр вообще. Значит автоматика подтверждает **логику** UI на Linux, но не подтверждает ни Wayland, ни поведение реальных декораций, ни скриншоты на живом экране.
4. **Native-стенд ENOSPC — workflow `native-disk-full.yml` содержит только `windows-latest` и `macos-latest`,** потому что Linux-ветка (реальный ENOSPC на tmpfs) была доказана раньше, локально в песочнице (evidence `docs/reviews/2026-10-16-qh-1c-remap-faults-ru.md`: «native ENOSPC Linux tmpfs PASS»).
5. **UI-спека ограничила Linux минимумом:** §10 для UI-1 — «macOS и Linux — перемещение и размер», т. е. единственные обязательные для Linux ручные пункты это UA-03 + перемещение. Всё, что «в стиле Windows 11» (UA-01, UA-02), по определению не про Linux.
6. **Приёмка WP4.1/4.2 была привязана к одной платформе** — решение D-36 в чек-листе: «реальная Windows-машина (Windows 10, 1920×1080 @100 %)». Linux-профиль (`XDG_DATA_HOME`, права каталога, сетевые ФС) в тот протокол просто не входил.
7. **UI-4 печатную приёмку сузили до win+mac** (остаток в issue #276: «приёмка печати на Windows/macOS»).
8. **Подпись.** QH §9.2 прямо говорит: для Linux — checksum/provenance и, при выбранной policy, detached manifest/package signature; «не представлять её как аналог Gatekeeper для standalone файла». Поэтому в G5b нет «linux-пункта», и это честное решение, а не пропуск.
9. **Среда исполнения агента — Linux.** В песочнице можно только запускать автотесты; «живой экран» на любой ОС агент подтвердить не может, поэтому ручные пункты формулируются там, где они не дублируются CI.

**Где это реальная дыра (и её надо закрыть, а не объяснять):**

| ID | Gap на Linux | Что добавить в приёмку |
|---|---|---|
| **LX-1** | Frameless-оболочка на **Wayland**: decorations, `FramelessWindowHint`, ресайз/перетаскивание, масштаб 150/200 % | Строка в UA-03/UA-20: GNOME Wayland + KDE Wayland + X11 без композита (i3/openbox). В UI-спеке это предусмотрено запасным путём `apply_maximized_to_work_area()` «там, где системное развёртывание ведёт себя плохо (часть оконных менеджеров Linux)» — но в матрице §11 строк нет |
| **LX-2** | Пути и блокировки персистентности | Пункт чек-листа: `$XDG_DATA_HOME/sonoforge` (по умолчанию `~/.local/share/sonoforge`), `.writer.lock` на **NFS/Samba** (flock на Linux ведёт себя иначе, чем на Windows), `chmod a-w`/`chattr +i` как аналог D4, ro-home |
| **LX-3** | Установщик и интеграция в окружение | `.deb` на чистой машине: ярлык `.desktop`, иконка, MIME-ассоциация DICOM, запуск из терминала и из DE; AppImage Presenter с флешки без прав |
| **LX-4** | Минимальный размер и hotspots | UA-03 помечен в §11 как «ручная + `hit_test`» без указания ОС → формально он уже [DUP-all], но в issue #281 не назван: **зафиксировать Linux в issue #281** |
| **LX-5** | Тема «как в системе» | UA-16 в матрице — только «Windows в тёмном режиме»; для Linux нужен аналог (`QT_QPA_PLATFORMTHEME=gtk3/gnome`, тёмный GTK, `Adwaita-dark`) |
| **LX-6** | Инверсивный аудит | UA-19 без Linux: `Orca`, `Tab` в GTK-filechooser, фокус в native диалогах печати |
| **LX-7** | Диагностика | §11.2: на Linux логи лежат в `~/.local/share/sonoforge/logs` (не в `%LOCALAPPDATA%`), содержимое `crash.log` после сигналов SIGSEGV отличается — PHI-греп обязателен и на Linux |
| **LX-8** | ENOSPC на реальном ФС | Прогнать `scripts/measurement_disk_full_harness.py` не только на tmpfs, но и на ext4/xfs c quota и на сетевом mounted-томе: поведение `fsync`/retry отличается от tmpfs |
| **LX-9** | Матрица релиза | В #188 Linux стоит «один дистрибутив из поддерживаемых» — это минимум, не «по желанию»; предлагаю сделать `.deb` (Ubuntu LTS) обязательной 4-й конфигурацией наравне с win/mac |

**Итог по вашему второму вопросу (коротко).** Malо проверок для Linux — не потому что Linux «забыли», а потому что:
 (а) весь машинный контур (CI, Xvfb, автотесты, ratchet, контраст, скриншот-гейты) живёт на Linux и туда руками лезть незачем;
 (б) ручная часть писалась под те платформы, где автотестов меньше всего — Windows/macOS (решение D-36 в чек-листе WP4, «Windows/macOS-приёмка» в остатке UI-4, win+mac в workflow ENOSPC, «не представлять как аналог Gatekeeper» в QH §9.2);
 (в) UI-спека для Linux сознательно оставила минимум «перемещение и размер» (§10, UI-1), и именно это — плановый gap.
 При этом Release gate спеки QH требует документировать «native Windows/macOS/Linux scope», а релизный путь `.deb` — поддерживаемый и заявленный в README. Значит Linux не «лишний», а **недоописанный в приёмке**: его надо добавить строками LX-1…LX-9 и метками [DUP-all], как сделано в §0.2/§0.3, а не изобретать заново.

**Предложение по трекеру:** открыть один issue `ui, linux-acceptance` «Linux-эквиваленты UA-02/UA-16/UA-20 и LX-1…LX-9» и завести строки в матрицу §11 спеки (например UA-02L, UA-16L, UA-20L), иначе Linux-часть остаётся «вне формальной приёмки», хотя именно на Linux живут реальные рабочие станции отделения.

### 1.2. Ручная приёмка UA-01 — Snap Layouts — **[OS:win, Windows 11]**

> Дублировать не нужно: на Windows 10, macOS и Linux пункт отмечается «н/п» (механизма нет). Максимум — одной строкой зафиксировать, что отсутствие Snap Layouts не ломает наведение на кнопку под `HTMAXBUTTON`.

1. Запустить сборку на Windows 11, открыть исследование, окно восстановлено (не maximized).

### 1.6. Ручная приёмка UA-20 — запасная системная рамка — **[DUP-all]**, а не только «RDP»

6. **Linux-эквивалент «проблемного окружения»:** запуск под Wayland (GNOME/KDE) и под X11 без композита (openbox/i3) → в обоих режимах переключатель «Системная рамка окна» даёт рабочее перемещение/ресайз, а «Фокус» (F) и радиальное меню не теряют мышиные события и не остаются «под» декорациями.

### 13.2. Ручная проверка, когда сборки подписаны — **[OS:win] + [OS:mac]**; для Linux — отдельная короткая строка

Поэтому на Linux проверяется только `sha256sum -c SHA256SUMS` (и detached-подпись пакета, если примете policy SIGN-6) — и никаких «Gatekeeper-подобных» обещаний в README/HELP/release notes.

   ```powershell
   Get-AuthenticodeSignature .\SonoForge-Setup-<ver>-x64.exe | Format-List Status,StatusMessage,SignerCertificate
   sigcheck -v SonoForge.exe            # если установлен Sysinternals
   ```
   **Ожидание:** `Valid`, цепочка доверяется, timestamp есть.
2. **SmartScreen:** первая загрузка из браузера и запуск — **без** «Windows protected your PC»; зафиксировать, что «Unknown publisher» исчез (для всех трёх ассетов: Setup, portable, Presenter).

5. **Сверка с `SHA256SUMS`/`latest.json`** — до и после проверки подписи; при расхождении — сразу FAIL и в #189.
6. Отрицательная проверка: подрезать байт в файле → подпись **должна** быть недействительна. На Linux тот же прогон, но относительно **хеша**: изменённый байт должен ломать `sha256sum -c SHA256SUMS` (подписи-аналога нет и обещать его нельзя).

### 16.1. Linux-часть самопроверки (перед ручной приёмкой на Linux)

```bash
# сессия под Wayland и под X11 без композита — два разных прогона
QT_QPA_PLATFORM=wayland  python -m echo_personal_tool      # GNOME/KDE Wayland
GDK_BACKEND=x11 XDG_SESSION_TYPE=x11 python -m echo_personal_tool   # openbox/i3 (без композита)

# «проблемное окружение» без железа: отключённая композиция
mutter --no-hardware-acceleration   # или: openbox / i3 без picom — ресайз и frameless без композитора

# 1) пути данных и блокировки (LX-2)
dir=${XDG_DATA_HOME:-$HOME/.local/share}/sonoforge/measurements; ls -la "$dir"
chmod a-w "$dir"   # отказ должен быть виден в UI, не молча; затем chmod u+w и повторная запись
chattr +i "$dir"   # immutable-каталог (требует sudo -i); не забыть chattr -i
sudo mount -o remount,ro "$dir"   # ro-mount: та же проверка на реальном ФС, не на tmpfs

# 2) ENOSPC на реальном ФС вместо tmpfs (LX-8): ext4 + project quota
sudo mkfs.ext4 -q /dev/loop10 && sudo mount -o prjquota /dev/loop10 /mnt/q10
sudo setfattr -n system.posix_acl_default /mnt/q10 2>/dev/null; true
python3 scripts/measurement_disk_full_harness.py --volume /mnt/q10   # ожидается реальный ENOSPC от ФС

# 3) PHI-греп логов и ZIP на linux-путях (LX-7)
logdir=${XDG_DATA_HOME:-$HOME/.local/share}/sonoforge/logs
grep -RniE "(/home/|/run/user|patient|accession|password|token)" "$logdir" | head -20

# 4) пакет и интеграция (LX-3, LX-9)
dpkg -l | grep -i sonoforge; sha256sum -c SHA256SUMS
cat /usr/share/applications/sonoforge.desktop | grep -E "^(Exec|Icon|MimeType)="
gio mime query inode/dicom 2>/dev/null || xdg-mime query default application/dicom

# 5) тема «как в системе» и контраст (LX-5, LX-6)
gsettings get org.gnome.desktop.interface color-scheme
QT_QPA_PLATFORMTHEME=gtk3 python -m echo_personal_tool   # тёмный GTK -> тёмный UI; затем Orca (Search → «Orca»)
```

> Если пункты 1–4 проходят только «на tmpfs» или только под Windows — это и есть подтверждение LX-gap'ов из §0.4: их нет ни в UA-матрице спеки, ни в чек-листе WP4.
