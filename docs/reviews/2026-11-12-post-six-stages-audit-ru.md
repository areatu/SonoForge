# Аудит после шести этапов: A1–A5 + S-03a

> **Снимок на 2026-11-12.** Краткий аудит `main` после PR #531 (`103dace`). Цель — не пересмотреть принятые срезы, а найти оставшиеся дефекты и слепые зоны проверки. Нативная GUI-приёмка, реальные PACS и клиническая валидация не выполнялись.

## Итог

Архитектурные срезы закрыты: у transport/display/zoom/label picker/контуров и download-batch есть один owner; координатор загрузки больше не читает приватные поля диалога. Ratchet'ы зелёные, `ruff` чистый. Но остаются **два функциональных дефекта в Orthanc-диалоге** и **слепая зона в тестовом ratchet'е**, из-за которой часть долга выглядит закрытой.

## P1. Функциональные дефекты

### 1. Частичный отказ при сохранении на диск уводит batch в cache-режим

**Где:** `presentation/orthanc_study_dialog.py`, `_on_single_study_failed` → `_start_next_download`; оба обработчика `failed` (cache и disk) подключены к одному методу.

**Что происходит.** Пользователь выбирает «Сохранить на диск», один из study падает. `_on_single_study_failed` вызывает cache-версию `_start_next_download()`, поэтому следующий worker получает `done → _on_single_study_done` вместо `_on_single_study_done_to_disk`. В результате успешные исследования после первого отказа не попадают в экспорт: диалог завершается через `_on_done`/`_on_partial_done` как cache-загрузка, `accept()` закрывает его, папка на диск не создаётся.

**Evidence.** Воспроизведение на текущем `main`: два исследования, первое `failed`, второе `done` → `result_data() == ("test-session", "")`, `accept()` вызван, `_on_disk_download_done`/экспорт не вызваны. Это не покрыто characterization-harness: сценарий «экспорт на диск» проверяет только успешный путь.

**Почему важно.** Это ровно пользовательский сценарий «частичный успех», ради которого делался disk-экспорт. Пользователь может потерять выбранный результат и получить cache-сессию вместо папки.

**Что сделать.** Ввести disk-aware обработчик отказа (или явный режим batch'а), который после `record_failed()` продолжает `_start_next_download_to_disk()`; добавить characterization-тест «disk: fail + success + partial export» до исправления.

### 2. Cache-сессия теряется без `clear_session` на нескольких путях выхода

**Где:** `orthanc_study_dialog.py`: `_on_cancelled` (строка ~3021), отмена экспорта в `_on_disk_download_done` (~2684), `_on_export_finished` (~2753), `_fail_disk_export` (~2804).

**Что происходит.** Эти пути выставляют `self._session_id = None`, но не вызывают `_cache.clear_session()`. Только `_on_failed` и `_force_close_if_still_downloading` очищают сессию. После отмены загрузки, отмены/завершения/сбоя экспорта каталог cache-сессии остаётся на диске и никем не адресуется; `clear_stale()` уберёт его только при следующем запуске.

**Почему важно.** Это не только место на диске: в cache лежат DICOM-файлы исследования. Для медицинского приложения «забытая» сессия — это ещё и риск хранения данных дольше, чем предполагает UX.

**Что сделать.** Очищать сессию на всех терминальных путях (или централизовать завершение batch'а в одном методе), добавить тесты с `Mock` cache на каждый путь. Отдельно решить, нужна ли сессия для повторного экспорта после сбоя; сейчас она уже недоступна, поэтому очистка безопасна.

## P2. Слепые зоны проверки и трекера

### 3. `check_test_private_access` показывает 0, хотя тесты массово ходят в приватные поля viewer

**Где:** `scripts/check_test_private_access.py`, `DEFAULT_SCOPE = ("tests/unit/test_*viewer*.py",)`.

**Что происходит.** Ratchet проверяет только файлы, в имени которых есть `viewer`. Но после A1–A5 приватные имена `ViewerWidget` живут и в других тестах: `test_area_tool_mode_wiring.py`, `test_presenter_view.py`, `test_lv_trace_contour.py`, `test_measurement_undo_redo.py`, `test_caliper_doppler_and_repeat.py` и др. По явным контурным/zoom-полям — **90 ссылок в 17 файлах**; по широкому набору приватных имён `ViewerWidget` — около 452 ссылок в 42 файлах. При этом отчёт говорит «0 references to private names in 0 viewer test files».

**Почему важно.** Зелёный private-access создаёт ложное впечатление, что тесты больше не зависят от реализации. Именно эти ссылки будут ломаться при следующей попытке уменьшить `ViewerWidget`, а baseline этого не покажет.

**Что сделать.** Расширить main scope на все `tests/unit/test_*.py` с фильтром по receiver'ам (`viewer`, `w`, `widget`) или добавить группу `ViewerWidget` по образцу `MainWindow`/`AppController`; записать фактический baseline и дальше только понижать. Для Orthanc-диалога — отдельная группа: в его тестах **101** обращение к девяти приватным именам batch'а.

## Что сознательно не считать новым дефектом

- **Размер `ViewerWidget`** (7 240 строк / 401 метод, модуль 8 132) — известный остаточный долг. План §6 прямо запрещает новые owner-срезы без доказательства второго владельца; это не задача «уменьшить любой ценой».
- **Дескрипторы совместимости** `_downloading`, `_stored_contours` и т.п. — осознанный мост для тестов, а не второй источник состояния. Но пункт 3 показывает, что мост пока не начал сокращаться.
- **Полный локальный `pytest tests/unit`** не укладывается в 30 минут; авторитет — CI-шарды. Это ограничение локальной проверки, не падение тестов.
