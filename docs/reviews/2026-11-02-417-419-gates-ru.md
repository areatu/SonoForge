Следующие две незаблокированные задачи — это не дефекты продукта, а **дефекты доказательства**: CI заявлял mypy strict, проверяя один интерпретатор, и архитектурный тест запрещал циклы, но не направление зависимостей. Их объединяет одно: зелёный гейт, который можно обойти, не заметив. Поэтому они сделаны одним PR, а не двумя.

## #417 — mypy strict на всей матрице 3.11–3.13

### Что было не так

`pyproject.toml` задаёт `python_version = "3.11"`, `strict = true`, `files = domain, imaging, application, infrastructure`. Job `lint` ставил из `uv.lock` mypy, PySide6 и `numpy` **без `--python-version`**, то есть 2.4.6 (пин для `<3.12`), и запускал голый `mypy` на Python 3.11. При этом `requires-python = ">=3.11,<3.14"` и маркеры `uv.lock` дают другой NumPy на 3.12/3.13:

| Интерпретатор | NumPy из `uv.lock` | Маркер |
|---|---|---|
| 3.11 | 2.4.6 | `python_full_version < '3.12'` |
| 3.12, 3.13 | 2.5.4 | `python_full_version >= '3.12'` |

То есть «mypy strict зелёный» было утверждением об одной ячейке поддерживаемой матрицы. В issue #417 со ссылкой на аудит указано **17 ошибок в 6 файлах** на Python 3.12 / NumPy 2.5.4. На замкнутом toolchain из `uv.lock` (mypy 2.4.0 + стабы NumPy 2.5.4, `--python-version 3.12` и `3.13`, `--no-incremental`, без кэша) воспроизводится **5 ошибок в 3 файлах**, одинаковых для 3.12 и 3.13:

| Файл | Строка | Ошибки | Классификация |
|---|---|---|---|
| `domain/services/doppler_grid_detector.py` | 53 | `operator`, `arg-type` | **код**: `np.median` в стабах 2.5.4 возвращает `np.floating`, а не `float`; сравнение с `ndarray` и передача в `np.where` больше не выводятся |
| `domain/services/depth_scale_detector.py` | 38 | `operator`, `arg-type` | **код**: то же для `np.std` |
| `domain/services/speckle_tracking.py` | 357 | `no-any-return` | **аннотация**: выражение деления потеряло точный `ndarray`-тип, нужен явный `cast`/приведение |

Все пять — код или аннотация, **дефектов сторонних стабов нет**: стабы NumPy корректно описывают скалярный тип, код на него неявно полагался. Остальные 12 ошибок из аудита на этом наборе версий не воспроизвелись (вероятно, другой mypy/другой набор установленных стабов: например, mypy 1.18.2 вообще не парсит `.pyi` NumPy 2.5.4 — они требуют синтаксиса 3.12+). Мы **не объявили их ложноположительными**: вместо этого добавлена воспроизводимая матрица, которая в CI на реальных интерпретаторах напечатает точный лог; если там появятся дополнительные ошибки, они будут видны и классифицированы по факту, а не «закрыты» заранее. Лог воспроизведения (до правок) сохранён в этом обзоре: `Found 5 errors in 3 files (checked 262 source files)` для обеих целевых версий.

### Что сделано

**Код (без новых подавлений).** В двух детекторах редукции явно обёрнуты в `float(...)`; в `speckle_tracking` возврат приведён к `np.asarray(..., dtype=np.float32)`. Это убирает зависимость вывода от того, какой скалярный тип вернул NumPy в конкретной версии, а не глушит ошибку. Счётчик `check_type_ignores.py` не изменился: 178 подавлений, 0 bare, 0 без причины. `pyproject.toml` не тронут — версия для матрицы приходит из CLI, конфигурация остаётся единой для разработчика.

**CI.** Добавлен job `typecheck` с `fail-fast: false` и матрицей `["3.11", "3.12", "3.13"]`. Каждая ячейка:

1. ставит реальный интерпретатор через `actions/setup-python@v7`;
2. вызывает [scripts/typecheck_matrix.sh](../../scripts/typecheck_matrix.sh) `<версия>` — ту же команду, что разработчик запускает локально;
3. скрипт ставит **все** инструменты из `uv.lock` и выбирает NumPy через `locked_version.py numpy --python-version <версия>`, сверяет `sys.version_info` с запрошенной ячейкой, запускает `python -m mypy --python-version <версия>` и отдельно проверяет, что mypy сообщил `no issues found in N source files` с `N > 0`. Прогон с нулём проверенных файлов (например, пустой `files` или случайная смена каталога) считается провалом, а не успехом.

**Агрегатный гейт.** `test` получил `typecheck` в `needs`, `TYPECHECK_RESULT: ${{ needs.typecheck.result }}` в env и `|| "$TYPECHECK_RESULT" != "success"` в условии; `build` по-прежнему ждёт `[lint, test]`. Без этого матрица была бы «информативной» проверкой, которую можно удалить, не уронив обязательный гейт.

**Гейт самого гейта.** [scripts/check_typecheck_matrix.py](../../scripts/check_typecheck_matrix.py) (только stdlib, шаг `lint`) читает `ci.yml` как текст, разбирает job'ы по двухпробельным заголовкам и требует: ровно три версии в матрице, `fail-fast: false`, вызов общего скрипта, `setup-python`, маркерно-зависимый пин NumPy, no-op guard, `typecheck` в `needs`/env/условии агрегата, сохранение mypy в `lint` и `UV_PYTHON_DOWNLOADS: never`. Шесть тестов в [test_typecheck_matrix.py](../../tests/unit/test_typecheck_matrix.py) мутируют копию workflow (убрать 3.13, заменить job на `echo`, выкинуть `typecheck` из `needs`, убрать проверку результата) и проверяют, что guard падает. Это characterization-тесты проводки, а не парсер YAML: у CI нет YAML-зависимости в lint.

### Граница локального доказательства

В песочнице нет реальных интерпретаторов 3.12/3.13: `uv python install` упирается в TLS к GitHub releases (`UnknownIssuer` / handshake EOF), а `pip install` cp312-колёс под 3.11 невозможен. Поэтому локально:

* `scripts/typecheck_matrix.sh 3.11` на реальном 3.11 — `Success: no issues found in 262 source files`, плюс guard `mypy strict checked 262 source files`;
* `mypy --python-version 3.12` и `--python-version 3.13` в изолированном venv, где `site-packages/numpy` заменён на **точный wheel 2.5.4 из `uv.lock`** (SHA256 сверён) — также `262 source files`, 0 ошибок;
* до правок эта же конфигурация воспроизводила ровно 5 ошибок из таблицы выше.

Это **статическое** доказательство типов: mypy анализирует код под целевой версией и целевыми стабами, но не исполняет его. Полноценные интерпретаторы 3.12/3.13 ставит `actions/setup-python` в CI — именно для этого и добавлена матрица. Вывод «всё работает на 3.12/3.13» из локального прогона не делается; он будет сделан по зелёным трём ячейкам PR.

## #419 — направление кросс-слойных импортов

### Инвентарь (AST, не grep)

[scripts/check_layer_directions.py](../../scripts/check_layer_directions.py) обходит `src/echo_personal_tool/**/*.py`, резолвит абсолютные, относительные (`from ..application import …`) и package-level (`from echo_personal_tool import application`) импорты и сохраняет для каждого запрещённого ребра файл, строку, модуль назначения и класс зависимости: `module` (рантайм), `lazy` (внутри функции), `type-only` (`if TYPE_CHECKING:`). Гейтятся все три: ленивый импорт всё равно связывает слои, а type-only — всё равно решение о владельце контракта.

Итог на снимок: **29 импортов, 25 уникальных рёбер, 19 записей baseline** в [layer_direction_allowlist.json](../../tests/architecture/layer_direction_allowlist.json).

| Направление | Импортов | Файлов | Суть |
|---|---|---|---|
| `infrastructure → application` | 11 | 7 | адаптер читает контракт/политику потребителя; 1 type-only и 1 lazy в `server_client_factory.py` |
| `ui → presentation` | 6 | 4 | листовой виджет тянет хелперы оболочки |
| `ui → infrastructure` | 12 | 9 | в основном `infrastructure.i18n` (`tr`), плюс `safe_diagnostics` и 2 lazy `infrastructure.profile` в `strain_window.py` |

Точные рёбра `infrastructure → application`: `dimse_client.py:20 → application.transport_policy`; `measurement_codec.py:42 → application.study_measurement_session`; `orthanc_client.py:47 → application.transport_policy`; `server_client_factory.py:7 → application.dicom_query_service`, `:22` (type-only) и `:83` (lazy) → `application.services.dicom_retrieve_service`; `server_settings.py:13 → application.transport_policy`; `ui_scale.py:38,39,40` и `user_preferences.py:12 → application.preferences_contract`.

Разрешённое обратное направление: `presentation/main_window.py:173 → ui.strain_window` (в инвентарь запрещённых не входит). Точные запрещённые рёбра `ui → presentation`: `ui/cine_panel.py:14,15,16` (`cine_phase_strip`, `segment_labels`, `speckle_overlay`), `ui/control_panel.py:21` и `ui/summary_table.py:9` (`ui_metrics`), `ui/strain_window.py:32` (`segment_labels`).

Для контекста (разрешённые направления, не гейтятся): `application→domain` 138, `application→infrastructure` 136, `infrastructure→domain` 68, `presentation→application` 244, `presentation→domain` 204, `ui→domain` 9, `domain→imaging` 2. Слой `constructor` (по инвентарю: 14 → `infrastructure`, 14 → `presentation`, 1 → `domain`) в этот срез **не включён**: у него ещё нет согласованного владельца, и замораживать нерешённую границу было бы преждевременно; это явно записано в `decisions.constructor`. Полный список запрещённых рёбер — `python scripts/check_layer_directions.py --list`.

### Решения о владельце слоя

| Направление | Решение | Почему |
|---|---|---|
| `application → infrastructure` | **разрешено** | фасад приложения владеет адаптерами; это и есть целевое направление (136 существующих импортов) |
| `presentation → ui` | **разрешено** | корень композиции (`main_window.py`) монтирует листовые виджеты |
| `infrastructure → domain`, `ui → domain` | **разрешено** | адаптеры и виджеты используют контракты/значения домена |
| `infrastructure → application` | **запрещено** | контракт принадлежит потребителю, а не адаптеру, которому он понадобился; обратная стрелка к фасаду делает слой неперемещаемым |
| `ui → presentation` | **запрещено** | листовой виджет не должен тянуть оболочку; иначе `presentation` нельзя разбить, не тронув `ui` |
| `ui → infrastructure` | **запрещено** | тот же принцип, что в ratchet'е #307 для `presentation → infrastructure`: UI идёт через фасад приложения |

**Отдельно про `application/preferences_contract.py`.** Механический перенос в `domain/ports.py` **не сделан**. Четыре импорта из `infrastructure` (`ui_scale.py`, `user_preferences.py`) выглядят как «положить контракт в домен и забыть», но владелец контракта — приложение: это его схема пользовательских настроек, а не порт доменной логики. Перенос без решения о владельце поменял бы семантику зависимости и создал бы новый контракт в домене ради того, чтобы счётчик рёбер стал меньше. Решение зафиксировано в `decisions.contract_ownership` в baseline; при желании его нужно пересматривать отдельным issue с аргументом, а не в этом срезе.

### Baseline и что именно ломается

Формат записи: направление, исходный файл, карта `модуль → точное число импортов`, обязательные непустые `reason` и `issue`. Сравнение **точное**:

* новое ребро → `NEW forbidden edge … (file:line, kind)`;
* второй импорт уже разрешённого модуля → `GROWN … 1 -> 2 import(s)` (не «растёт молча»);
* исчезнувшее ребро или изменившееся число → `STALE …` (исправление нужно зафиксировать ревью baseline, а не автоматической правкой);
* пропущенная причина / issue / неизвестное направление / дубль → ошибка валидации baseline.

`--fix` намеренно отсутствует: в отличие от счётчиков, здесь любое изменение — решение о владельце слоя. Шаг `lint` запускает checker с `--github-summary`, который печатает полный инвентарь в job summary. Восемь тестов [test_layer_directions.py](../../tests/unit/test_layer_directions.py) покрывают: соответствие реального инвентаря baseline, разрешённые направления не гейтятся, новое ребро называется с файлом и строкой, относительные/package-level импорты учитываются, `type-only`/`lazy` классифицируются, рост и устаревание падают, запись без причины невалидна.

**Что намеренно не сделано:** ни одно историческое ребро не удалялось, код между слоями не перекладывался. Устранение вынесено в отдельные маленькие срезы, каждый — с characterization-тестом и с одновременным снятием своей строки baseline (не с `--fix`):

1. `server_client_factory.py` — 3 ребра (`application.dicom_query_service`, type-only и lazy `dicom_retrieve_service`). Перед разрывом зафиксировать тестом, какой клиент и с какими параметрами строит фабрика в DIMSE/DICOMweb-режимах; ports определить на уровне потребителя, если они действительно нужны.
2. `ui → presentation` (6 рёбер) — characterization-тесты форматирования `ui_metrics` и `segment_labels`/`cine_phase_strip`/`speckle_overlay`, затем перенос UI-чистых хелперов вниз по слою.
3. `ui → infrastructure.i18n` (9 рёбер) — отдельное решение о владельце перевода (`tr`); пока владелец не согласован, перенос был бы косметическим.
4. `infrastructure → application.transport_policy` (4 ребра) и `preferences_contract` (4 ребра) — один срез на «политику и настройки» с тестами чтения/записи настроек и сетевой политики; контракт остаётся у потребителя.
5. `measurement_codec.py` и lazy `infrastructure.profile` — по одному точечному срезу с тестом соответствующего формата/стартапа.

Каждый срез уменьшает baseline, а гейт не даёт ему одновременно вырасти в другом месте. Гейт `test_import_graph_has_no_cycles` и прежние архитектурные проверки (`domain → infrastructure` = 0, пустой allowlist `presentation → infrastructure`) остались зелёными: новый гейт ортогонален ацикличности. Ацикличный, но неправильно направленный граф теперь тоже виден.
