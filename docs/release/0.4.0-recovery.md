# Recovery of the published 0.4.0 release

This is a one-time recovery, **not a new build or a moved tag**. The public
v0.4.0 is incomplete until this procedure finishes successfully. The original
Release and Presenter runs built and smoke-tested their artifacts; the full
release verification failed because the original SBOMs omitted the application
version and the Windows checkout used CRLF in `uv.lock`. Presenter deliberately
did not attach its files after that failure.

The manually dispatched **Recover 0.4.0 release evidence** workflow uses only
the two original workflow runs and the tagged commit
`e91a770f3a9d4aefc08835b53ff8092a45e193a3`. It fails closed if the tag,
original source/run identities, recorded artifact hashes, original SBOM hashes,
smoke evidence, published full binaries, or lock hashes disagree. The existing
Windows lock hash is retained unchanged: for this exact tagged commit only,
verification accepts the hash of its CRLF checkout as equivalent to the
original LF lock bytes.

The staging tool retains the original full and Presenter binaries. It preserves
original SBOMs, build records, packaged smoke evidence and the original lock
in `v0.4.0-original-release-evidence.zip`. Corrected SBOMs add version-bound
metadata; amended build records retain original build facts and explicitly
point to the archive and the SHA-256 of the original record. Publication issues
new SBOM attestations for the original binaries before attaching the amended
metadata, Presenter files and their checksums. It does not replace full-profile
binaries or move the tag. `latest.json` is regenerated and attested afterwards.

1. Ensure PR checks and review have succeeded and this workflow is on `main`.
   Do not rerun the original Release or Presenter tag workflows: those use the
   unchanged, faulty code in the tag.
2. In GitHub Actions, run **Recover 0.4.0 release evidence** on `main` with
   `publish` **unchecked**. This is a dry run. Review every step and download
   `recovery-0.4.0-dry-run-verified`: staged matrix, checksums, SBOMs, build
   records and existing attestations must pass. Its `latest_json` entry is not
   verified at this stage because Presenter has not been attached yet. No
   release files or new attestations are published in a dry run.
3. Only after a successful dry run, run the same workflow on the **same main
   commit**, check `publish`, and enter that successful run's numeric ID in
   `dry_run_id`. The workflow rejects a different commit, branch or missing dry
   run. If main changes, run a fresh dry run before publication.
4. Wait for the publish run to pass. It downloads the release back and verifies
   the complete matrix, checksums, amended SBOM records, `latest.json` and
   attestations. Inspect `recovery-0.4.0-final-verification`, the public
   release assets and both checksum manifests before announcing success. A
   failed publish may leave partial metadata; review the failure and rerun only
   after checking the release. Repeated runs accept only the original metadata
   or the exact deterministic amendment, not unexplained replacements.

The two original runs' downloadable artifacts must still be available to GitHub
Actions. Their repository retention was reduced to one day. If they have
expired, **do not run publication**: the operator's separately saved archives
must first be restored through a separately reviewed recovery procedure. This
workflow does not accept arbitrary uploaded binaries. The `.deb` first-run
bootstrap, Presenter USB acceptance, OS signing/notarization and clinical
acceptance remain separate gaps; successful automation does not prove them.
